# 手动机器狗运动建图操作简版

适用：已完成4-1部署的香橙派、MID-360和FAST-LIO。沿用原遥控器控制，软件负责建图、记录；后半部分说明如何接入Nav2实现边建图边导航。

**前半流程保持：启动二维和三维建图 → 低速路线3次 → 振动工况3次 → 每轮保存与备份完整地图。后半改为：复用SLAM地图与位姿 → 接入Nav2规划和避障 → 对接机器狗速度控制 → 验证目标点导航 → 停车、保存并退出。**

当前可直接执行的是第2～4节原遥控建图流程。第5节为边建图边导航的集成和验证流程；现有4-2建图launch不启动Nav2，且关闭软件运动输出，本次文档修改不代表板端已完成导航部署。

## 1 实验目标和通过条件

| 项目 | 必做内容 |
| --- | --- |
| 手动路线 | `manual_walk`，同一路线3次，每次至少1米 |
| 振动工况 | `vibration`，已有允许步态或地面工况3次，记录实际条件 |
| 地图保存 | YAML、PGM、PCD及配套元数据整套保存，实际重载检查通过 |
| 后续边建图边导航 | 按第5节接入Nav2，使用SLAM位姿和实时地图导航；完成板端集成后再开展真机验证 |

本课前半保留FAST-LIO、扫描转换和slam_toolbox建图。SLAM本身同时估计本次地图坐标系中的位置与朝向，后半导航直接使用这套位姿关系，不再退出建图去启动AMCL，也不再做独立的AMCL重定位3轮。

本章不要求测量A点的map真值、房间周长或墙面ROI，不填写4-3的测量确认参数、不调用 `/lab_4_3/start_trial`。已有4-2参数中的 `reference_configured=false` 可保留，`reference_pose`、`reference_note`、`initial_pose` 不用于本章建图及SLAM导航流程。雷达外参和行走包络继续沿用已核对的实机配置。

卷尺真值用于绝对精度评估，不是SLAM建图或Nav2在线导航的启动条件。取消该项评分后，不给出未经独立验证的厘米级精度结论。

## 3 终端A启动建图

完成第2节检查、旧程序已全部退出后，用原遥控让机器狗站稳静止，再启动一份完整建图程序。与4-1一致，默认固定 `start_runtime=true`、`start_hardware=true`，不再用pgrep自动决定复用驱动：

```bash
(
  set -e
  source ~/catkin_ws_lite3dog/real_configs/lab4_1_remote_env.sh
  export ROS_DOMAIN_ID=43
  cd ~/catkin_ws_lite3dog
  test -f "$LIDAR_CONFIG"
  mkdir -p "$HOME/catkin_ws_lite3dog/results" "$HOME/catkin_ws_lite3dog/real_configs"
  SESSION="$(mktemp -d "$HOME/catkin_ws_lite3dog/results/4_2_remote_XXXXXXXX")"
  echo "本次结果目录：$SESSION"

  ros2 launch lite3_lab_4_2 experiment.launch.py \
    mode:=real start_runtime:=true start_hardware:=true \
    lidar_config:="$LIDAR_CONFIG" \
    lidar_xyz:="$LIDAR_XYZ" lidar_rpy:="$LIDAR_RPY" \
    initial_body_height:="$BODY_HEIGHT" \
    robot_length_m:="$ROBOT_LENGTH" robot_width_m:="$ROBOT_WIDTH" \
    footprint_padding_m:="$FOOTPRINT_PADDING" \
    native_execute:=false enable_real_motion:=false \
    autostart:=false rviz:=false \
    map:="$SESSION/maps/robot_dog_auto_map.yaml" \
    result_dir:="$SESSION"
)
```

只启动一次，静置约10秒等待初始化，保留A。创建结果目录不代表启动成功；启动失败时先处理A的报错，不把空目录写成当前会话。

仅在明确使用独立启动、同域43、JSON正确且数据持续更新的单一雷达驱动时，才将 `start_hardware:=true` 改为 `false`；旧LIO和适配器仍须退出。普通流程保持true。机器狗已在启动前站稳；初始化期间保持静止，不在初始化过程中起立或走动。

### 3.1 终端B确认数据

每次A重启后，在B重新取得实际目录。先清除旧变量，查询失败时不继续记录或保存：

```bash
source ~/catkin_ws_lite3dog/real_configs/lab4_1_remote_env.sh
export ROS_DOMAIN_ID=43
unset SESSION

for ATTEMPT in 1 2 3; do
  RUN_DIR="$(timeout 8s ros2 param get /lab_4_2 result_dir 2>/dev/null | sed -n 's/^String value is: //p')"
  if [ -n "$RUN_DIR" ] && [ -d "$RUN_DIR" ]; then
    SESSION="$RUN_DIR"
    break
  fi
  sleep 2
done

if [ -n "${SESSION:-}" ] && [ -d "$SESSION" ]; then
  printf '%s\n' "$SESSION" > "$HOME/catkin_ws_lite3dog/real_configs/lab4_2_current_run.txt"
  echo "本次结果目录：$SESSION"
  ros2 param get /course_sensor_adapter use_sim_time
  ros2 param get /laser_mapping use_sim_time
  ros2 param get /laser_mapping point_filter_num
  ros2 param get /laser_mapping filter_size_surf
  ros2 param get /laser_mapping filter_size_map
  ros2 param get /lite3_course_continuous_adapter execute
  ros2 topic info /livox/lidar
  ros2 topic info /livox/imu
  ros2 topic info /Odometry
  ros2 topic info /course/lio_points
  timeout 8s ros2 topic hz /course/imu
  timeout 8s ros2 topic hz /course/odom
  timeout 8s ros2 topic hz /scan
  timeout 8s ros2 topic delay /course/odom
  ros2 topic info /map
  if [ -f "$SESSION/stream_health.json" ]; then
    cat "$SESSION/stream_health.json"
  else
    echo '尚未取得本轮4-2健康文件，请等待初始化，不开始走测。'
  fi
  timeout 5s ros2 topic echo /course/lio/quality --once
else
  echo '未取得有效4-2目录。检查A、域43和初始化状态，不启动第二份launch。'
  ros2 node list
fi
```

| 检查项 | 应满足 |
| --- | --- |
| 实际目录 | B读出的目录与A本次成功启动的目录一致 |
| 两个 `use_sim_time`、连续适配器 `execute` | 均为False，与4-1原遥控实机模式一致 |
| 减负参数 | 依次为 `3`、`0.5`、`0.5` |
| 上述四个原始/LIO话题 | 每个 `Publisher count=1`，没有重复发布 |
| 数据更新 | IMU、odom、scan持续更新；当前里程计延迟正常，无持续时间戳回退 |
| 二维地图 | `/map`已发布，只有本轮预期地图发布者 |
| 本轮4-2健康与LIO质量 | `stream_health.json`每秒更新、`ready=true`、`streams_ready=true`、`reasons=[]`、`session_faults=[]`；LIO质量已初始化、当前有效且无锁存故障 |

`timeout`到时结束检查正常；`False`是本模式预期设置。若参数仍为 `1、0.1、0.1`，按4-1核对实际公共包和旧进程，正常重启后再检查，不放宽时延阈值。

4-2使用本会话自己的 `stream_health.json`：正常时应为 `ready=true`、`streams_ready=true`、`reasons=[]`、`session_faults=[]`，其中 `streams` 分别列出IMU、里程计和LIO质量。每轮记录还保留 `admission_health`、`stream_health` 和 `faults`。4-1特有的 `imu_stationary_ready` 和 `/course/trajectory` 不直接套用于4-2；也不读取旧4-1的健康文件。本章前半仍按本轮服务响应、`trials.json`、地图重载报告及手动路线和振动两类记录核对；后半导航按第5节单独验证，不使用AMCL收敛评分。

同时观察终端A：初始化附近的少量空点告警需结合后续数据判断；持续出现 `No Effective Points!`、体素索引溢出 `Integer indices would overflow`、里程计位置异常跳变或点云持续消失时，先原遥控停车，按第3.3节取证，不继续下一轮或覆盖已有合格地图。二维 `/map` 会保留此前内容，画面中仍有旧地图、话题仍有发布者或时延较低，都不能单独证明当前LIO正常。不要仅按报错文字继续调大体素或放宽阈值。

目录确认后，把A中首次和持续告警的时间及附近输出保存下来。在B做只读检查：

保留本次完整故障目录，包括 `stream_health.json`、`trials.json`、每轮健康诊断及 `faults`、各类汇总、已保存地图及其校验报告；已有地图只复制到独立目录，不用新的 `save_map` 覆盖。会话故障锁存后，不在原会话反复开始或保存；若故障发生在活动轮次，按第4.2节结束并保留该轮失败事实。随后原遥控按正常流程趴下，回A按 `Ctrl+C`，等待整套程序正常退出，按第2节检查残留，再用第3节创建新的结果目录。先重新通过第3.1节检查，确认点云恢复、位置连续且无持续匹配告警，再继续测试。新旧会话均保留，不把重启后的正常状态追记为旧故障轮通过；不单独重启记录节点来复用已故障的FAST-LIO，也不因这类故障重置参考配置、改动体素或放宽时延阈值。

## 4 手动路线和振动工况各做3次

标记A点、朝向和同一路线，每轮至少1米并实际返回、对齐、停止。振动工况使用已允许的地面条件，不敲打或松动雷达；更换步态须重新核对包络。

### 4.1 开始一轮

终端B先设置工况和本类轮次：

```bash
KIND=manual_walk
ROUND=01
ros2 param set /lab_4_2 trial_kind "$KIND"
ros2 service call /lab_4_2/start_trial std_srvs/srv/Trigger '{}'
```

开始服务成功后，原遥控走路线并停下。变量只区分备份，不重置内部计数。

### 4.2 停下后保存地图

先检查本轮覆盖、当前点云、本会话 `stream_health.json` 和A中LIO状态。持续匹配失败、位置异常或点云消失时，转第3.3节，跳过本节的 `save_map`，保护此前合格地图。无此类故障时再保存：

```bash
ros2 service call /lab_4_2/save_map std_srvs/srv/Trigger '{}'
```

服务返回只表示请求已受理；PCD重载校验在后台进行。刚受理时 `map_save_result.json` 为 `pending=true`、`success=false`，并记录本次 `requested_ros_s`；这是等待状态，不立即判为保存失败。稍后查看，确认报告属于本次请求，不把上一轮遗留的成功结果当成本轮完成：

```bash
cat "$SESSION/map_save_result.json"
cat "$SESSION/map_validation.json"
```

等待本次 `map_save_result.json` 为 `pending=false`、`success=true`、`valid=true`、`map_topic_matches_metadata=true`，并出现 `completed_ros_s`；`map_validation.json` 也应为 `pending=false`、`valid=true`。核对分辨率 `0.05 m`、PCD点数大于0且XYZ有效，再结束：

```bash
ros2 service call /lab_4_2/finish_trial std_srvs/srv/Trigger '{}'
```

保存未结束时等待，不重复请求，也不开始下一轮。健康轮次若 `finish_trial` 返回 `success=false` 并提示“后台地图保存/校验尚未完成”，本轮尚未结束；保持停车，等上述JSON完成后再次调用 `finish_trial`。若已发生传感器或LIO故障，即使校验仍在进行也可调用 `finish_trial` 落盘失败记录，不再 `save_map` 覆盖旧地图。未保存或保存已失败时，也可直接 `finish_trial` 留下失败记录，不反复等待旧文件变成成功。

- 10 Hz连续输入时，50/100帧相当于5/10秒的数据量。队列只保存等待处理的消息，不能保证任意中断都塞得下；长期处理能力不足或TF停止推进时，扩大队列会保留更多旧数据。本机Nav2守卫还要求动态TF源年龄不超过1秒，不能靠几秒积压进入导航。
- Humble官方实现中，transform_tolerance传给回调内的TF转换，作为查询等待超时；查询仍使用点云原时间，不能“查询未来一点”或恢复已移出缓存的旧TF。MessageFilter本身的队列等待也不能仅靠改这个值解决。
- 该官方节点没有use_header_stamp开关：输出扫描直接保留输入header。scan_time是输出消息中的周期字段，不是发布限频器；改它不会自动降低节点实际处理频率。
- 可以减少显示或地图可视化刷新，或在确认算力不足后评估扫描支路只处理较新帧；降低处理频率与把数据排队数秒是两件事。此次先保持既有频率，不降低里程计、动态TF和局部避障的时效要求。

| 雷达时间来源 | 官方driver2依据数据包time_type选择雷达同步时间或主机时间；不能直接往JSON/YAML加 `use_hardware_time: true` 就认定硬件同步已启用。板端驱动实际实现、固件版本及PTP锁定状态仍需核对，不把未核验的V1.4.3当作本机升级要求 |
| /scan时间戳 | 应非零、逐帧向前，当前约10 Hz时相邻帧约0.1秒；若跳帧需同时看源时间差、实际接收间隔和LIO质量，不把任何毫秒抖动一律判错。10秒观察只作初查，继续做下面的180秒检查 |
| 系统时间/PTP | timedatectl只说明主机状态：主机NTP同步不证明雷达已PTP锁定；离线局域网NTP未同步也不能单独证明当前时间戳错误。若采用PTP，还需核对真实主时钟、从时钟锁定和偏移，不能只开启一个选项；运行期间不手动跳系统时间 |
| QoS | 发布者Reliable、订阅者Best Effort可以兼容；发布者Best Effort、订阅者Reliable不兼容。看每个端点，不要求全链路一律相同；本机扫描转换和slam_toolbox使用传感器QoS，点云RViz订阅保持Best Effort |
| SLAM参数 | 本机transform_timeout预期0.5秒（读取实际值确认），minimum_time_interval=0.15秒；先保留。前者参与TF等待，也参与map→odom的时间戳有效期，不能简单调大来修复已停止的输入 |
| TF与数据链 | 本机是 `map→odom→base_footprint→base_link→lidar_link`；扫描取 `/course/points_raw`，保留采集时间，再变换到base_footprint。它不是把FAST-LIO的配准点云直接接到扫描转换；LIO仍提供所需的动态机身TF |

不要直接拿 `/tf` 中数组第0项与扫描比较：它可能不是需要的那条边。`tf2_echo`用于初查连通，Nav2的check继续按实际map→odom、odom→base_footprint核验。正确发布在 `/tf_static` 的外参对任意查询时间有效，不应因它的显示时间旧就忽略“早于全部TF缓存”的报错；应查整条链中的动态TF、重复发布及扫描时效。

**重点观察map→odom的时间是否推进。** 保持A、D运行且未arm，在B执行下面三项短时初查（每项15秒到时退出正常）：

```bash
timeout 15s ros2 run tf2_ros tf2_echo map odom
timeout 15s ros2 topic delay /scan
timeout 15s ros2 topic delay /course/odom
```

本机Humble实现中，`restamp_tf=false` 时，map→odom时间戳来自最近进入SLAM回调的扫描时间加transform_timeout；当前timeout约0.5秒，因此可近似比较 `TF源年龄 ≈ 对应扫描源年龄 − 0.5秒`，不能要求两者延迟数字直接相等。TF每秒仍有很多消息，也可能只是重复同一个旧时间；要看 `At time` 是否持续向前。三个命令是依次抽查，不是同步逐帧配对，细查要使用同一时段的stamps记录。

| 同一时段的表现 | 下一步排查 |
| --- | --- |
| 原始点云/IMU和scan接收都中断 | 先查雷达、网络、驱动、主机调度和时间源，不能仅归咎SLAM |
| 原始点云继续到达，odom及LIO质量失败，scan随后停止 | 查LIO输入和质量故障，以及扫描转换所需的动态机身TF |
| scan与odom都新鲜，map→odom的At time停住 | 查SLAM是否实际接收扫描、该时刻TF能否查询、过滤队列及版本行为 |
| scan源年龄逐渐增大，map→odom随之滞后，而odom仍正常 | 查扫描支路的排队和转换延迟；保留扫描时间，消除积压，不改旧时间为now |

不把 `restamp_tf=true` 或增大timeout作为这次断流的修复；也不以降低/map刷新频率替代动态TF与扫描时效。之前出现的两秒以上输入中断仍需解决，TF2锁修复不等于该问题已经消失。

依据：[Livox官方时间戳实现](https://github.com/Livox-SDK/livox_ros_driver2/blob/master/src/comm/pub_handler.cpp)、[ROS 2 QoS兼容规则](https://github.com/ros2/ros2_documentation/blob/humble/source/Concepts/Intermediate/About-Quality-of-Service-Settings.rst)、[SLAM Toolbox Humble实现](https://github.com/SteveMacenski/slam_toolbox/blob/humble/src/slam_toolbox_common.cpp)。PTP/硬件时间源尚未核实的部分仍标为待核对，不宣称全部完成。
