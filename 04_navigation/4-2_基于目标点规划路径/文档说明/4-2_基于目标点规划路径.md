## 启动A前：雷达路由和采样时间

在B先确认eth0有LOWER_UP且已分配192.168.1.50，再补充雷达专用路由并检查两条链路：

```bash
ip -br link show eth0
ip -br -4 addr show eth0
sudo ip route replace 192.168.1.3/32 dev eth0 src 192.168.1.50
ip route get 192.168.2.1
ip route get 192.168.1.3
export REAL_TOOL="$AUTO/nav2_real_lab.py"
python3 -B "$REAL_TOOL" network
sudo systemctl start lite3-lidar-ptp.service
systemctl is-active lite3-lidar-ptp.service
```

雷达路由应为`192.168.1.3 dev eth0 src 192.168.1.50`。无网线载波或无本机.50地址时，增加路由本身不能补出雷达数据。192.168.1.10作为当前管理入口保留，机器狗192.168.2.x内部网络按实际网关和转发关系核对，不能仅凭SSH管理地址判定运动链断开。REAL_TOOL的network命令沿用旧直连路由判据；使用内部网关时，失败只表示不符合它的固定预设，须结合实际本体网络配置判断。本章不使用旧native arm/serve流程，REAL_TOOL的network命令只核对网络。

已安装的`lite3-lidar-ptp.service`只在eth0向雷达提供PTP时间，采用本机接口支持的软件时间戳，设置masterOnly/free_running且不授予修改系统时间的能力。A要求该服务运行，并使用经过校验的Livox驱动：只接受设备的PTP/GPS采样时间；未同步时明确等待，不再以主机收包时刻作为本章测量时间。默认启动8秒等待用于时钟服务准备；PTP正常时A日志应出现`Livox timestamp_type=1 require_sensor_sync=1`，实际数据仍由A/B新鲜度检查确认。

这是实体机，各节点继续`use_sim_time=false`。同步来源改变、LIO质量锁存或位姿异常后，保留旧证据，完整退出A/C/D/E/F再新建本轮地图；不能只重开F，不能给旧TF补当前时间，也不能仅调大队列继续使用故障状态。

## 雷达网络与B启动检查

A要求雷达192.168.1.3经eth0、源地址192.168.1.50直连，检查UDP端口可绑定，再写入本轮`lidar_runtime.json`和`lidar_network.json`；路由不符时明确拒绝，不自动切换Wi-Fi接收地址。公共MID360配置文件和传感器外参不改写，时间戳使用前述设备PTP/GPS采样时间。`lidar_network.json`记录接口、实际接收IP、端口及原始/运行配置哈希。该步骤只检查本机网络准备情况，不能证明雷达已连接或正在发数据。

正常直连时应看到eth0有链路、地址192.168.1.50，且到192.168.1.3的路由经eth0。只有管理Wi-Fi的192.168.1.10可达，或能ping通192.168.1.3，均不能代替实际雷达数据检查。eth0显示NO-CARRIER时先检查雷达供电、网线和接头。

B的`session prepare-nav`现在先等待真实的新鲜odom、scan、已启用保护的LIO有效状态、SLAM地图和map→base_footprint TF，最长10秒；缺失时明确报“未生成导航目录”，并将原因写入本轮`bringup_health.json`，不继续创建导航配置。先修复A再执行B，不能靠enable、提高超时或重启D补出缺失的里程计。

在B查看网络证据（RUN先按本章指针读取）：

```bash
ip -br address
ip route get 192.168.1.3
cat "$RUN/lidar_network.json"
cat "$RUN/bringup_health.json"
```

较早版本的会话可能没有新增的JSON文件；重启A后会生成网络记录，执行新版B后生成健康记录。
